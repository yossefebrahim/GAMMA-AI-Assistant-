The build journey — five issues, fixed in order

The Dart port was clean on the first analyze. Getting a green native build took five fixes; the last is a documented limitation, not a defect in our code.

  1. Code signing. keychain-access-groups requires a real Apple Developer certificate. Removed it from the debug profile (kept in release) so local builds work without a signing team.
  2. Deployment target. The Runner target still compiled at macOS 10.15 while flutter gemma requires 11.0. Bumped MACOSX_DEPLOYMENT_TARGET to 11.0 across all three build configs.
  3. Build-phase cycle (ours). The flutter gemma Podfile script phase implicitly depended on the native-cache directory. Marked it always_out_of_date = '1' (out of dependency analysis).
  4. Build-phase cycle (Flutter's). Flutter Assemble's native-assets step lists the cache dir as an input while its output dylib lives inside it — a self-cycle Xcode 26.5 rejects. Cleared by flutter clean (fresh dependency graph).
  5. The cycle recurs on incremental builds — confirmed upstream after 3 fix attempts. A clean build succeeds; a subsequent flutter build/flutter run without flutter clean re-derives the cyclic graph and fails. I tried: (a) alwaysOutOfDate on my own phase — fixed it for clean builds; (b) disabling Xcode-26 asset-symbol generation — no effect; (c) alwaysOutOfDate on Flutter's own “Flutter Assemble” Run Script — no effect, because that phase declares the native-cache dir explicitly via the Flutter-generated FlutterInputs.xcfilelist (the dir contains its own output dylib → a self-cycle the new build system rejects on incremental). Only a Flutter SDK or flutter_gemma change fixes it, and the plugin is pinned for the Android baseline. Workaround: always clean-build macOS (now wired as an opt-in BUILD_MACOS=1 gate in verify.sh). cf. flutter/flutter #134256, #153842.

What changed

Governance — constitution amendment (v2.0.0 → v2.1.0, MINOR)

macOS (Apple Silicon) is now a sanctioned secondary target. Principle IX no longer lists “non-Android platforms” as an absolute non-goal; Principle V gains a macOS device tier (Apple Silicon required, Intel rejected, ≥16 GB for the E4B tier); Principle VIII allows file-import acquisition where there is no background-download service. Privacy, offline-first, and seam-testability are explicitly preserved. A maintainer note flags that you may prefer a MAJOR bump if you read relaxing the non-goal as backward-incompatible.

Known limitations & decisions for you

Limitations / deferred

  • Clean-build only on macOS (incremental cycle — confirmed upstream after 3 fix attempts).
  • No in-app model picker — needs the file_selector dep (a dependency decision left for you).
  • Composer Enter-to-send deferred — fiddly Flutter focus/key interception on a multiline field; risky to ship without manual desktop verification. Recommended: Focus.onKeyEvent on the field's focus node, gated via isMacOsProvider.
  • Source-URL chips are a silent no-op on macOS — needs url_launcher (dependency decision).
  • BYOK key persistence on a debug build needs the keychain entitlement → a dev-team signed build, or set useDataProtectionKeyChain:false in the key store seam.
  • Inference unverified on Metal — needs a model file; A34 spike findings don't transfer.

Decisions to make

  • App Sandbox on (App-Store viable, needs a signing team) vs off (simplest local dev)?
  • Add file_selector for the model-import picker, and url_launcher for source-URL chips?
  • Accept the “always clean-build macOS” rule, or invest in an upstream cycle fix?
  • Ship image input on macOS at all (grounding is broken regardless)?
